# V3 Experiment Design: What TraderBot Should Provide on Day One

## Question

**What should TraderBot provide to a freshly deployed agent so it can form a defensible probability estimate and make good trade decisions?**

The experiment varies **what TraderBot provides**, not the agent or the methodology. The same LLM agent (glm-5.1:cloud) sees different context levels and we measure which leads to better decisions.

## Why V3 — Problems with V2

### Problem 1: Band Market Delta Is Fundamentally Wrong

For `strike_type=between` (band) markets, V2 computes:

```
delta = center - |forecast - center|
```

This produces absurd values like +88.6. It's not a meaningful "distance to threshold" — it's essentially "forecast distance from absolute zero within the band." A delta of +88.6 tells the agent "direction is YES-positive" but gives no sense of magnitude or probability.

**The real question for band markets**: Given forecast μ°F with known uncertainty σ°F, what is P(actual temp ∈ [floor, floor+1))?

A forecast of 88.9°F with ±2°F uncertainty has the band [90,91) about 1.1°F above — there's a small but nonzero probability mass inside that band. But our delta (+88.9) says "strongly YES" — exactly wrong when the point estimate is below the band and the market might settle NO.

**Evidence**: KXHIGHTSEA-26MAY10-B66.5 settled YES, but the T-0 forecast was 61.9°F — 4.1°F below the [66,67) band. Market price was 0.97 YES while the delta computed +61.9 (positive → YES direction). The forecast was catastrophically wrong, and the delta gave no useful information.

### Problem 2: Point-Estimate Thinking Ignores Forecast Uncertainty

All four V2 treatments give the agent a single number (forecast temperature, delta, or probability derived from delta). But weather forecasts are probability distributions, not point values. At T-4, ±5°F is realistic; at T-0, ±1.5°F is realistic. The agent cannot reason about band markets without understanding this spread.

### Problem 3: structured_prob Is a Monotonic Transform of raw_data — Zero Incremental Info

BinCal's `sigmoid(delta)` is a deterministic function. If you know the forecast and threshold, you can compute the probability yourself. The LLM agent can do this arithmetic in its head. Providing it as a "TraderBot estimate" is redundant — it contains no new information.

### Problem 4: Forecast Accuracy Data Exists But Is Not in Any Treatment

We can compute per-city, per-lead-time forecast accuracy from Kalshi settlement results:

| City | T-0 MAE | T-0 Bias | T-4 MAE | T-4 Bias |
|------|---------|----------|---------|----------|
| Austin | 1.6°F | +1.3°F | ~3.5°F | +1.3°F |
| Minneapolis | 2.9°F | +2.5°F | ~5.5°F | +2.5°F |
| NYC | 1.7°F | +0.6°F | ~3.5°F | +0.6°F |
| Seattle | 1.5°F | -0.0°F | ~3.0°F | ~0.0°F |

This is genuinely independent information — the agent CANNOT derive "Austin forecasts tend to be 1.3°F too warm" from a single forecast value. This is the missing piece.

### Problem 5: Control Treatment Didn't Mirror Production TraderBot

V2's control gave just market price and trade volume. But TraderBot's current production pipeline (`traderbot analyze` + `traderbot signals`) provides:
- Market details and orderbook
- Implied probability from mid-price
- Technical indicators (RSI, Bollinger bands, EMA crossover)
- Combined signal direction and confidence

The control should mirror what an agent actually receives from TraderBot today, not a stripped-down version that no real deployment would use.

## V3 Treatment Design

Each tier adds information the agent **cannot derive** from lower tiers AND that reflects what the agent actually faces in production on Kalshi.

### Treatment 1: control (mirrors current TraderBot main branch)

This treatment replicates what `traderbot analyze` + `traderbot signals` currently provide an agent:

```
Market: {market_title}
City: {city}
Resolution date: {date}
Strike type: {strike_type_description}

Market analysis:
- YES price: {yes_price}  NO price: {no_price}
- Implied probability: {implied_prob} (from mid-price)
- Trade volume: {trade_count} trades in this window
- Open interest: {open_interest}

Technical indicators:
- Signal direction: {signal_direction} (yes/no/neutral)
- Signal confidence: {signal_confidence}
- RSI: {rsi} ({rsi_interpretation})
- Bollinger position: {bollinger_position} (near lower/middle/upper band)

This is timestep {timestep} of 5. You have {remaining} timesteps remaining before settlement.

{prior_decisions_section}

Based on market data and technical indicators, decide:
- buy_yes: if you believe the true probability is significantly above the YES price
- buy_no: if you believe the true probability is significantly below the YES price
- skip: if the edge is thin or you lack confidence

Respond ONLY with a JSON object:
{{"decision": "buy_yes" | "buy_no" | "skip", "estimated_prob": float, "confidence": float, "reasoning": string}}

estimated_prob: your estimate of the probability the market resolves YES (0.0 to 1.0)
confidence: how confident you are in your estimate (0.0 to 1.0)
reasoning: brief explanation of your thinking
```

**Rationale**: This is exactly what a TraderBot agent receives today — market prices, implied probability from orderbook, and technical indicators (RSI, Bollinger bands, momentum). NO weather forecast data, NO forecast accuracy, NO city-specific bias. The agent must rely entirely on market crowd wisdom and price action.

**What this mirrors in production**:
- `traderbot analyze` → market details + orderbook + implied probability
- `traderbot signals` → direction, confidence, estimated_prob from combined signals
- `traderbot trade --estimated-prob X --confidence Y` → the agent provides its own probability estimate

### Treatment 2: raw_data

```
[Everything in control, plus:]

Forecast data:
- Current forecast: {forecast_temp}°F high for {city}
- Forecast source: Open-Meteo ensemble model
- Forecast age: {days_before} days before resolution

Measurement uncertainty for {city}:
- At T-0 (day of): MAE {t0_mae}°F, systematic bias {t0_bias}°F ({bias_direction})
- At T-2 (2 days before): MAE {t2_mae}°F, systematic bias {t2_bias}°F
- At T-4 (4 days before): MAE {t4_mae}°F, systematic bias {t4_bias}°F
- These accuracy figures are computed from {n_settled} prior Kalshi weather markets

Forecast delta: {delta}°F from threshold ({delta_direction})
```

**Rationale**: The agent now knows the forecast PLUS how reliable that forecast is at this specific lead time for this specific city. This is data it CANNOT derive from the current forecast alone. A forecast of 88.9°F means something very different for Austin (bias +1.3°F, MAE 1.6°F) vs Minneapolis (bias +2.5°F, MAE 2.9°F).

**Key change from V2**: Delta for band markets uses **signed distance to nearest boundary** instead of the broken `center - |forecast - center|` formula.

### Treatment 3: structured_prob

```
[Everything in raw_data, plus:]

TraderBot Probability Estimate:
- P(YES): {p_yes:.1%}
- P(NO): {p_no:.1%}
- 95% confidence interval: [{ci_lower:.1%}, {ci_upper:.1%}]
- Computed from: {n_historical} historical forecasts with similar delta
- Method: Bayesian update using city-specific error distribution N(μ_adj, σ²)

Where:
  μ_adj = forecast - city_bias
  σ = city_mae_at_lead_time
  P(YES) = integral of normal PDF over the YES region
```

**Rationale**: Takes the accuracy data from raw_data and does the computation the agent can't easily do in its head: integrating a normal distribution over the region that settles YES. For a `less` market at 64°F with forecast 62.3°F and Austin bias +1.3°F and σ=1.6°F, the adjusted forecast is 61.0°F and P(temp < 64) = 96.9%. For a band market [90,91) with forecast 88.9°F and σ=1.6°F, P(temp ∈ [90,91)) = 9.2%.

**Critical**: The probability computation for band markets now accounts for uncertainty. A forecast 1°F below the band with σ=2°F gives P≈19%, while a forecast 1°F below with σ=0.5°F gives P≈2%. This is why uncertainty matters.

**Key change from V2**: Replaces sigmoid(delta) — a monotonic transform of delta — with a proper Bayesian probability using known error distributions. This IS incrementally informative over raw_data because the agent can't easily integrate a normal distribution over a band threshold in its head.

### Treatment 4: calibration_bundle

```
[Everything in structured_prob, plus:]

Forecast Trajectory:
- T-4: {f4}°F ({delta4:+.1f}°F from threshold)
- T-3: {f3}°F ({delta3:+.1f}°F)
- T-2: {f2}°F ({delta2:+.1f}°F)
- T-1: {f1}°F ({delta1:+.1f}°F)
- T-0: {f0}°F ({delta0:+.1f}°F)
- Trend: {trend} over past {trend_days} timesteps ({trend_slope:+.1f}°F/step)
- Forecast range: {min_f}°F - {max_f}°F ({range:.1f}°F spread)

Historical settlement rate for similar forecasts:
- In {n_similar} prior markets with delta within ±{bin_width}°F of {delta}:
  YES settled: {yes_pct:.0%} ({yes_count}/{n_similar})
- With city-specific bias correction applied: {adj_yes_pct:.0%}
```

**Rationale**: Adds temporal dynamics and historical settlement rates. The trajectory tells the agent whether forecasts are converging (confidence should increase) or diverging (confidence should decrease). The historical settlement rate gives empirical calibration beyond the theoretical probability.

**Key additions over structured_prob**:
1. **Forecast trajectory** — shows convergence/divergence pattern across timesteps
2. **Trend slope** — quantitative rate of change (°F/timestep)
3. **Forecast range/spread** — how much forecasts have swung (Minneapolis: 14.7°F range vs Austin: 4°F range)
4. **Historical settlement rate** — "In 23 prior markets where delta was -1 to -3°F, YES rate was 13%" — empirical calibration data

## Probability Computation for V3

### For `less` markets (P(temp < threshold))

```python
from scipy.stats import norm

def prob_less(forecast, threshold, city_bias, city_mae):
    mu_adj = forecast - city_bias  # Adjust for systematic bias
    sigma = city_mae
    return norm.cdf(threshold, loc=mu_adj, scale=sigma)
```

### For `greater` markets (P(temp > threshold))

```python
def prob_greater(forecast, threshold, city_bias, city_mae):
    mu_adj = forecast - city_bias
    sigma = city_mae
    return norm.cdf(floor + 1, loc=mu_adj, scale=sigma) - norm.cdf(floor, loc=mu_adj, scale=sigma)
```

### For `between` (band) markets (P(temp ∈ [floor, floor+1))

```python
def prob_between(forecast, floor, city_bias, city_mae):
    mu_adj = forecast - city_bias
    sigma = city_mae
    return norm.cdf(floor + 1, loc=mu_adj, scale=sigma) - norm.cdf(floor, loc=mu_adj, scale=sigma)
```

**This is the critical fix**: Band markets now get proper probability based on the known error distribution, not an absurd delta like +88.6.

## Metrics

### Primary

| Metric | What it measures | How to compute |
|--------|-----------------|----------------|
| Brier score | Probability calibration | mean((estimated_prob - outcome)²) — lower is better |
| P&L (cents) | Trading performance | Sum of (decision_quality × position_size) across all trades |
| Win rate | Decision accuracy | % of trades where the agent's direction agrees with settlement |

### Secondary

| Metric | What it measures |
|--------|-----------------|
| Decision distribution | skip vs trade ratio per treatment |
| Anchoring distance | |estimated_prob - TraderBot_prob| per treatment |
| Timing | Which timesteps agents choose to trade vs skip |
| Reasoning quality | Does the agent reason about uncertainty and bias? |

### Scoring Emphasis

Weight contended markets more heavily — blowout markets offer near-zero edge regardless of treatment. A treatment that helps agents skip blowouts and trade contended markets accurately is genuinely better.

## Key Implementation Changes from V2

1. **Control mirrors production TraderBot** — Includes market prices, implied probability, technical indicators (RSI, Bollinger, momentum), not just bare market price
2. **Replace band delta with probability computation** — Use `norm.cdf` integration with known error distributions, not `center - |forecast - center|`
3. **Add forecast accuracy stats to raw_data** — City-specific MAE and bias at each lead time, computed from Kalshi settlement results
4. **Replace sigmoid with Bayesian probability in structured_prob** — Use actual error distributions, not monotonic transforms
5. **Add forecast trajectory to calibration_bundle** — Show evolution across timesteps with trend and range
6. **Fix price extraction** — No future peeking (only trades before window end)
7. **Strike thresholds from API** — Use `strike_type` and `floor_strike` from Kalshi API directly
8. **Score with emphasis on contended markets** — Blowout markets provide minimal signal

## Forecast Accuracy Computation

```python
        forecasts = get_previous_runs_forecast(city, target_date, lead_time)
        settlement = get_kalshi_result(city, target_date)  # NWS CLI

        # Aggregate across all available markets for this city
```

These stats tell the agent: "For Austin at T-0, your forecast differs from settlement by MAE 1.6°F with a +1.3°F warm bias. At T-4, MAE grows to 3.5°F." This is the critical missing information that makes forecasts actually useful for decision-making.
